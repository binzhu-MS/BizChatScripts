# CoMet ↔ Foundry — Criterion Discrepancy Audit

Joint audit of criterion discrepancies between the **CoMet** reasoning-checklist
implementation
([`metric_logic.py`](../../../../../../CopilotMetrics/sources/dev/MetricDefinition/cometdefinition/metrics/bizchat_reasoning_checklist/logic/metric_logic.py))
and the **Foundry** session scripts under `sessions/`.

This document carries only **patterns and open issues** that remain useful for
future debugging. Resolved cases and per-snapshot history are intentionally
pruned after merge; recover history from git if needed.

**Ground rules.** Foundry is the source of truth for **criterion semantics**;
CoMet must follow Foundry. Diagnose each discrepancy on its own merits (read the
actual script and the actual CoMet code) — never fix by "match the other side".
When the bug is in CoMet logic, fix `metric_logic.py`. When it is in a Foundry
script or session data, fix `sessions/*.json`. When it is shared pipeline
(aggregator, denominator, naming), the side owning the pipeline fixes it.

---

## 1. Pipeline reminder (both sides)

Both CoMet and Foundry consume the same **Seval scrape**: the model under
test is invoked once, and its Sydney telemetry blob
(`{"telemetry":{"metrics":[{"serviceName":"DeepLeoImprovedNetworking","output":"…toolInvocations:[…]"}]}}`)
is cached as the per-row inference output. Both reuse this cached telemetry,
so model behavior is byte-identical between runs.

Each side then runs its own evaluation pipeline:

| Stage | Foundry | CoMet |
|---|---|---|
| Parse telemetry → canonical tool-call JSON | per-criterion `parsingScript` ("Foundry Pre-Eval Script"); stdout becomes `{{text}}` | `_extract_tool_calls` / `_format_tool_call_json` over the last turn's L1 iteration of `EvaluationData` |
| Score row | Foundry `script` (Python, no LLM when `prompt.messages == []`) reads `{{text}}`, `{{utterance}}`, `{{label}}`, …, and `print`s a number | criterion fn in `CRITERIA_REGISTRY` of `metric_logic.py`, receives `text, **ctx` and returns an int |
| Aggregate | `check_reasoning_checklist.py` (averages `scriptOutput`, falls back to `assessment` when empty) | `execute()` emits one score per session-row × criterion; aggregation in downstream tooling |

"Non-LLM" means **stage 2 has no judge LLM**. M is always involved (in the
scrape) but is not the source of any divergence between the two implementations.

---

## 2. Terminology — "combined-tool calls"

In Sydney session scripts and CoMet logic, **combined tool** means the unified
`office365.search` / `office365_search` / `web.search` / `office365.open` /
`office365.find` family, carrying an inner `queries: [{domain, query}, …]`
array. The opposite is the **legacy per-domain tools**
(`search_enterprise_emails`, `search_enterprise_chat`, …). CoMet detects
combined style via `_is_combined_tool` against `_COMBINED_TOOL_MARKERS`.

When adding or normalising tool detection on either side, remember spelling
variants exist for the same logical tool: `office365.search` ↔
`office365_search`, `bing.search` ↔ `bing_search`, `office365.open` ↔
`office365_open`, `office365.find` ↔ `office365_find`, plus `search_web`.

## 3. Diagnosis playbook

When a row in the comparison report differs by ≥ 5 abs / 10 % rows OR ≥ 5
score points in either arm:

1. **Read both sides' actual code** for that criterion before forming a
   hypothesis. "Match the other side" is never a valid fix criterion.
2. **Classify the gap**:
   - *Score gap, same denominator* → criterion-logic divergence (either side
     could be wrong; usually a missing skip clause, wrong score scale, or
     wrong empty-input behaviour).
   - *Denominator gap* → either Foundry has unscraped dataItems still in its
     session (see §4.2), or CoMet has an upstream label/segment filter
     Foundry doesn't.
   - *0/0 in one arm only* → suspect Worker phantom-duplicate (§4.3) or
     aggregator merge collision.
   - *Criterion present on one side, absent on the other* → almost always
     stale `resultsv2` in the packed session: the per-criterion `script` /
     `parsingScript` was updated by a later repack but the embedded
     `dataItemsEvaluationOutputs` were generated by an earlier eval run
     against the old scripts. Symptom: `scriptOutput` contains `Traceback`
     errors that the *current* script cannot produce on the *current*
     `dataItemsOutputs`. **Fix: rerun Foundry evaluation on the affected
     sessions**; do not patch the aggregator to swallow the tracebacks.
3. **Check empty/parse-failure branches first** — they cause the most
   asymmetric bugs:
   - Foundry `raise SystemError/ValueError` *drops the row* (no number
     printed → row not in numerator or denominator).
   - Foundry `print(0)` *keeps the row* (denominator counts it as a fail).
   - CoMet `return _SKIPPED` (= −1) drops the row.
   - CoMet `return 0` keeps the row as a fail.
   These must be aligned on a per-criterion basis: don't assume symmetry.
   Some criteria (e.g. `IsEnriched(TruePositive)` vs `(TrueNegative)`) are
   **intentionally asymmetric** on empty inputs.
4. **Inspect template-variable provenance** when in doubt — re-derive what
   `{{text}}`, `{{label}}`, `{{user_profile_*}}` actually resolve to from the
   session JSON + response file, rather than from the script's comments.

## 4. Recurring discrepancy patterns

These are the patterns we have hit repeatedly. Use them as starting hypotheses
before diving into a new symptom.

### 4.1 Empty/parse-failure branch asymmetry

The single most common class of bug. CoMet defaults to `_SKIPPED` (= drop row);
Foundry varies per script — some `print(0)` (keep row, fail), some `raise`
(drop row), some print no number at all (drop row).

- *Symptom:* CoMet score is **higher** than Foundry on the same dataset AND
  CoMet denominator is **lower** than Foundry.
- *Where to look:* the empty-queries / no-files-domain / `JSONDecodeError`
  branches in both implementations.
- *Fix direction:* whichever side is wrong on the semantics of "no evidence
  on a positive-label row" must change to match the metric's intent (almost
  always: keep the row, score 0).
- *Failed-inference vs. legitimately-empty-input:* P/R-style Foundry
  scripts with an "all-empty → 1.0" base case (e.g. CHI_LB precision /
  recall) need a separate guard against rows where inference itself
  produced nothing, or those rows get a vacuous 100. The robust
  discriminator is the parsed `{{text}}`: `not tool_calls and
  Usage.get("prompt_tokens", 0) == 0` — `prompt_tokens == 0` is the
  signal a real call never happened. A legitimate "no tool call
  expected" row still has non-zero `prompt_tokens` and correctly stays
  in the base case. Signal a skip by printing an `Error: …` line and
  `raise SystemExit(0)` (Foundry classifies a script that emits no
  numeric line as *Skipped*). The CHI_LB fix (PR 5207084) is the
  reference implementation.
- *Validation-loop vacuous-pass variant:* this is **not** limited to P/R
  "all-empty → 1.0" base cases. Any Foundry script that *iterates*
  `tool_calls` and `print`s a pass after the loop (e.g.
  `is_a_nice_serialized_JSON`) **vacuously prints 100** on a
  failed-inference row, because the loop body never executes. The naïve
  empty-string guard `if not {{text}}.strip()` does **not** catch this:
  the Foundry pre-eval still emits a well-formed but empty payload
  `{"tool_calls": [], "Usage": {"prompt_tokens": 0, …}}`, so `{{text}}`
  is non-blank. The reliable discriminator remains `prompt_tokens == 0`
  (no inference happened) — add that skip, not a text-emptiness check.
  CoMet drops these rows via the same `prompt_tokens == 0` guard, so the
  gap is denominator-only (§4.2) until Foundry matches.

### 4.2 Denominator semantics — unscraped utterances

Foundry session `dataItems` may include utterances that produced **no
inference output** during the Seval scrape. Foundry's script can still "run"
on them (with `{{text}}` empty) and emit a score; CoMet's pipeline drops such
rows pre-scoring.

- *Symptom:* Foundry denominator ≈ full `dataItems`; CoMet denominator =
  full `dataItems` − unscraped rows.
- *Diagnosis:* compare `len(dataItems)` (or `sessionInputs[0].dataItems`) vs
  `inference[*].dataItemsOutputs` non-empty count. Per-arm.
- *Tools:* `C:\working\Foundry\local\code\audit_utterance_coverage.py`
  audits every session.
- *Foundry-side fix when criterion logic is correct:*
  `C:\working\Foundry\local\code\fix_foundry_session_denominator.py` prunes
  unscraped dataItems (keeps utterances scraped in **both** arms, rewrites
  top-level `dataItems` (1-based) and `sessionInputs[0].dataItems`
  (0-based), re-numbers indices, writes `.bak`).
- *Watch out:* per-arm scraping can be asymmetric (e.g. ctrl 135 / treat
  134). A shared base session can only hold one denominator; intersection
  is the conservative choice.

### 4.3 Worker phantom duplicate arm / criterion entries

The Foundry Worker (`JobProcessor.cs`) can emit a duplicate arm entry
(same `promptId` / `sydneyId`) or a duplicate criterion entry (same
`criteriaId` within an arm) with **empty inner dicts**, due to a
non-atomic `FirstOrDefault`→`Add` race in the four `Initialize*Results`
helpers under concurrent data-item processing. Frequency observed
across 1,288 packed sessions: ≈ 0.23 %.

- *Detection signature:* two arms / criteria sharing the same id, one
  populated and one with empty `dataItemsEvaluationOutputs` /
  `parsedInferenceFileLocations`. Downstream `.First(…)` lookups
  always pick the first, so the second becomes a silent stub. When a
  consumer indexes by *position* instead of by id, the stub corrupts
  that arm's score.
- *Fix and reproduction:* see
  [foundry-phantom-arm-race-fix.md](../../../../../../Foundry/local/docs/foundry-phantom-arm-race-fix.md)
  (Worker `resultsInitLock` + Sydney `_enforce_unique_arm_ids`
  invariant check in `check_reasoning_checklist.py`, plus a
  deterministic unit-test sketch).
- *Ops signal:* grep pipeline logs for `WARNING: [duplicate-arm]` —
  every line names the arm id, kept/dropped cell counts, and session
  index, so triage requires no rerun.

### 4.4 LLM-judge criteria without a Python post-processor

Criteria where `prompt.messages` is non-empty but `script` is absent:
`assessment` is populated, `scriptOutput` is empty.

- *Foundry UI reference* (`RatingBasedEvaluation.ts → runCriteria`):
  `scriptOutput = !criteria.script ? criteriaOutput : invokePythonScript(...)`
  — when there is no post-processor, the judge text *is* the score.
- *Aggregator behaviour (correct, already in `check_reasoning_checklist.py`):*
  fall back to `assessment` when `scriptOutput` is empty. Parser
  `extract_number_start_or_end` covers first-line float → last-line float →
  JSON `.score`.

### 4.5 Profile / payload parsing: JSON ≠ Python literal

Session-level fields like `sharedContext.user_profile_fluxV3 / fluxV2` are
authored as **single-quoted Python literals**, not valid JSON. A naïve
`json.loads(s)` returns `{}` and silently masks model behavior.

- *Fix pattern (`safe_load_user_profile`):* try `json.loads`, then
  `ast.literal_eval`, then `json.loads(s.lower().replace("'", '"'))` as
  fallbacks. Apply to both `s` and `s.lower()` candidates so that
  case-preservation is the default (downstream usually lowercases anyway).
- *Foundry runtime substitution scope:* the Worker resolves a `{{key}}`
  placeholder against the **merge** of `sessionInputs[s].sharedContext`,
  `dataItems[i].input`, and the per-row `PythonScriptDataModel`
  (`text`, `utterance`, `criteria`, `assessment`, `promptId`,
  `promptName`) — in that precedence order, later merges winning. See
  `FoundryToolkitWorker/Services/JobProcessor.cs` (lines 1010, 1077,
  2080, 2181, 2389, 3702, 3754). So a session-shared value like
  `user_profile_fluxV3` *is* substitutable from `sharedContext`.

### 4.5c Are these sharedContext fields recoverable from the Seval scrape?

Yes for user-profile (richer than sharedContext), partially for
runtime context, and not needed for boilerplate. Inspected via
`local/code/inspect_scrape_full.py` against

set-membership tests.

### 4.6 Tool-name spelling variants in detection regexes

Detector regexes that look for `office365.search` (dot) miss
`office365_search` (underscore), the form the Sydney parsingScript emits.
Same for `bing.search` / `bing_search`, `office365.open` / `office365_open`,
`office365.find` / `office365_find`, and `search_web`. When adding a
detector, accept **both** spellings, and add `search_web`.

### 4.7 Empty/missing `label` field — implicit-positive convention

Some sessions (`triggering_email`, `triggering_email_shared_mailbox`,
`prompt_triggering_fetch_event`, `meeting_intent_parameter`) use *omission*
of `label` to mean "positive" (or "in-scope"), and only set `label` for the
exclusion classes (`negative`, `ambiguous`).

- *Symptom:* `if label in ("negative", "ambiguous"): raise` never fires
  because `{{label}}` resolves to `""`.
- *This is intentional* on those sessions; the script is correct. The
  matching CoMet criterion may apply a different (often smaller)
  positive-set definition — confirm with the metric owner whether the
  denominator gap is a bug or a known dataset-convention difference.

### 4.8 Response-field semantics (Foundry response files)

Verified rules — the aggregator and any downstream consumer must respect
them:

| Criterion shape | `scriptOutput` populated | `assessment` populated | Read |
|---|---|---|---|
| Non-LLM (`prompt.messages == [] && prompt.promptTemplate == ""`) | yes (Python script stdout) | no (Worker skips judge at `JobProcessor.cs` ~L1421) | `scriptOutput` |
| LLM-judge + post-processor | yes (script's number) | yes (judge text) | `scriptOutput` |
| LLM-judge, no post-processor | **no** | yes (judge text) | `assessment` (aggregator fallback) |

Blanket-clearing `assessment` / `scriptOutput` across session JSONs is
**not** a fix — the aggregator overwrites both on the next run.

### 4.9 Stale `resultsv2` in repacked sessions

When the build pipeline rewrites a session's `parsingScript` / `script` but
does **not** regenerate `resultsv2[*].evaluation[*].criteria[*].dataItemsEvaluationOutputs`,
the saved `scriptOutput` reflects the **old** script's behavior on the old
inputs. The aggregator then sees `Traceback` errors (e.g.
`KeyError: 'tool_calls'`) that the *current* script could not produce on the
*current* inference output (because the current `parsingScript` normalises
it). Result: every row fails to parse, and the criterion either reports
`0.00 (0 rows)` or vanishes entirely.

- *Detection:* run the current `parsingScript` on one row of
  `resultsv2[0].inference[0].dataItemsOutputs[*]` and confirm the output is
  a clean `{"role":"assistant","tool_calls":[…]}`. If the saved
  `scriptOutput` is `KeyError: 'tool_calls'`, the eval was clearly run
  against the raw telemetry blob — i.e. before the parsingScript was wired
  in. Any repack must be followed by a rerun.
- *Fix:* rerun Foundry evaluation on the affected sessions; do not patch
  the aggregator to swallow these tracebacks (that masks real script bugs).

### 4.10 Aggregator: register every criteriaId, even if all rows drop

Defensive hardening already in `check_reasoning_checklist.py`: the
per-evaluation accumulator touches `per_crit_totals[crit_id]` for every
criterion encountered, before the per-row parse loop. When every row's
`scriptOutput` is unparseable, the criterion still emits `0.00 (0 rows)` so
it appears in `results.md` (matching the Playground UI) instead of being
silently dropped. The `0 rows` count is the diagnostic signal that
something upstream is wrong (typically §4.9).

### 4.11 Shared criteriaId across sessions (label collision in `results.md`)

A criteriaId must be globally unique to its evaluation logic. If two sessions
declare the same `criteriaId` with **different** `name` / `script`,
`check_reasoning_checklist.py`'s first-write-wins lookup will relabel one
session's results with the other session's name. The compare step then sees
a Foundry-only row and a CoMet-only row that are actually the same metric.

- *Detection:* the same UUID appears in `evaluationStrategy.criteriaList` of
  two sessions with different `name` fields.
- *Fix:* change one session's `criteriaId` to a fresh UUID (rewrite every
  occurrence in the session JSON: `evaluationStrategy.criteriaList[*].id`,
  `sessionInputs[0].criteriaIds`, per-`dataItem` `criteriaIds`).
- *Defensive hardening (already in `check_reasoning_checklist.py`):*
  `criteria_data` is scoped per session (`{session_basename: {criteriaId:
  …}}`), so even if a future collision is introduced, each row gets the
  correct label.

### 4.12 Nested-orchestration tool-call asymmetry (SearchAgent / workberry sub-calls)

The two implementations read tool invocations from **physically different
telemetry channels** in the same Sydney scrape, and only CoMet's channel
carries sub-orchestrator (SearchAgent / workberry / pagination) invocations.
On any session where a router tool delegates to a sub-agent that in turn
calls the concrete domain tool, **CoMet sees the inner tool, Foundry does
not.** (Resolved 2026-05; both sides now mirror the recursive walk.)

- *Symptom:* CoMet score is **higher** than Foundry on segments where a
  loop2/workberry/pagination flight is enabled, for any criterion that
  detects a combined-tool name (domain recall, `CHI_LB_*`,
  `GC_tool_precision/recall`, anything matching `_COMBINED_TOOL_MARKERS`).
  Foundry sees only the router (`search_office365`,
  `api_tool_search_tools`, …) which is **not** in the combined-tool
  marker set, so those criteria score 0 on Foundry and ≥ 0 on CoMet.
- *Channels (verified empirically on
  `local/Seval/489852_huiwen/Sydney_Raw_Responses/control_sydney_response_00086a6d….json`
  via `local/code/_diag_workberry_nested.py`):*

  | Side | Path | Sees nested? |
  |---|---|---|
  | CoMet | `evaluationData.turnData[-1].orchestrationIterations[0]` walked recursively through `modelActions[*].toolInvocations` **and** `nestedOrchestrations[*]` — see `_extract_tool_calls` / `_iter_orchestrations` in [`metric_logic.py`](../../../../../../CopilotMetrics/sources/dev/MetricDefinition/cometdefinition/metrics/bizchat_reasoning_checklist/logic/metric_logic.py) | **Yes** (recursive) |
  | Foundry | `telemetry.metrics[serviceName == "DeepLeoImprovedNetworking"].output.toolInvocations` (flat array, L1 only) — see `extract_tool_calls_from_deep_leo` in [`foundry_preeval_script.py`](../../foundry_preeval_script.py) and the trim path in [`build_foundry_eval_sessions.py`](../../build_foundry_eval_sessions.py) `trim_sydney_response` | **No** (flat) |

- *Empirical example* (same scrape, both channels):

  ```
  CoMet view (recursive):                       Foundry view (flat L1):
    L0 root            -> search_office365         search_office365
    L1 root.nested[0]  -> office365_search
  ```

  CoMet captures **2 invocations** (router + concrete domain tool);
  Foundry captures **1** (router only).

- *Fix (landed, 2026-05):* both sides now mirror the recursive
  per-iteration walk — CoMet via `_extract_tool_calls` /
  `_iter_orchestrations`; Foundry via the per-iteration synthesis in
  `build_foundry_eval_sessions.py` plus the concatenating
  `extract_tool_calls_from_deep_leo`. Ground rule: Foundry owns
  **semantics**, not **completeness of the tool-call list** — the inner
  tools are the same physical calls the router triggered and must be
  counted. Regression: a fixture cut from `_diag_workberry_nested.py`
  asserts `extract_tool_calls_from_deep_leo` returns both
  `search_office365` and the inner `office365_search`.

- *Reusable diagnostic:* `local/code/_diag_workberry_nested.py` takes any
  raw Sydney response and prints both views side-by-side. Use it before
  and after the Foundry fix to confirm parity.

- *CoMet side:* **no change.** CoMet's recursive walk is semantically
  correct — the inner tools ARE the calls the model made.

### 4.13 Failed eval submission → false "CoMet-only" rows

A failed rebuild-side evaluation POST (e.g. HTTP 500 from
`.../api/v2/evaluation/async`) creates no evaluation resource, so that
session contributes **no rows** to the rebuild-side `results.md`. The
comparator then buckets its criteria as **Foundry (CoMet)-only**, which
looks like a semantic divergence but is not.

- *Detection:* check the run's `*-results/error-log.txt` for a non-200
  status on the missing session's JSON. The same session submitted in an
  adjacent round returns 200 with both criteria present on both sides.
- *Not size-related:* much larger packs (tens of MB) in the same run
  submit fine; the 500 is transient/server-side.
- *Fix:* resubmit just the affected session JSON — no code or manifest
  change. (Observed once on `fetch-email/prompt_triggering_fetch_email`,
  snap 8; cleared on resubmit in snap 11.)

### 4.14 First-tool-call-only vs iterate-all scoring divergence (multi-`office365_search` rows)

A whole class of deterministic 🔼 (CoMet-higher) gaps comes from a CoMet
criterion that **returns on the first matching tool call** while the
Sydney `script` **iterates every matching tool call** and folds them
together. When a turn fans out into ≥2 of the same tool (workberry /
multi-hop), the first call and a later call can disagree, and the two
sides then score the row differently.

- *Canonical case (R3, `files_scope_url_folder / URL_preserved_rate`):*
  CoMet's `_files_url_preserved_strict` looped `tool_calls` but `return`ed
  on the **first** `office365_search`. Sydney's `(strict)` script loops
  **all** `office365_search` calls, AND-accumulates `url_no_change`
  **globally** (never reset between calls; last printed number wins), and
  `raise`s `ValueError` — dropping the whole row — on any `office365_search`
  whose files-domain query list is empty. Net Sydney semantics: *"every
  files-domain query across every search must contain the URL, else 0;
  and if any search has no files-domain query, drop the row."*
- *Symptom:* on rows with ≥2 `office365_search` calls where the **first**
  preserves the URL but a **later** one drops it, CoMet = 100, Foundry = 0
  → CoMet higher. The sibling `(loose)` (OR-accumulated, monotonic) rarely
  flips, which is why only the strict variant diverged. A secondary
  denominator gap comes from Sydney's mid-loop `raise` dropping rows CoMet
  still scores.
- *Empirical confirmation:* [`_diag_r3_v2.py`](../code/_diag_r3_v2.py)
  replays both policies on the same extracted tool calls (snap-11 packed
  session). The `(CoMet=100, Foundry=0)` bucket was **47 ctrl / 15 treat**
  rows — *every one* with `n_office365_search = 2` — reproducing the
  +20.39 / +7.17 deltas exactly; the 3-row ctrl denominator gap matched the
  `(*, DROP)` buckets.
- *Fix (CoMet, since Foundry = semantic truth):* iterate **all**
  `office365_search` calls, AND/OR-accumulate the flag globally, and
  `_SKIPPED` if **any** such call has no files-domain queries (mirroring the
  `raise`). Applied to both strict and loose in `metric_logic.py`
  (`_files_url_preserved_strict` / `_loose`); 5 multi-search regression
  tests added; full suite 582 ✅.
- *Reusable check:* when triaging any deterministic 🔼 on a criterion that
  inspects tool calls, grep the CoMet function for an early `return` inside
  the `tool_calls` loop and compare against whether the Sydney `script`
  `break`s/returns or runs to completion. A `return`-on-first vs
  run-to-completion mismatch is this bug.

### 4.15 "Any tool call" vs "recognized search query" scoring divergence (agentic router tools)

A CoMet criterion that scores on the **mere presence of `tool_calls`**
diverges from a Sydney `script` that scores on the presence of a
**recognized search query**, whenever the treatment model routes through a
high-level **agentic router tool** instead of emitting a concrete search.

- *Canonical case (R1, `retain_i_me_my_in_query / wrong_reasoning`):*
  CoMet's `_wrong_reasoning` returned 100 if `data["tool_calls"]` was
  non-empty. Sydney's script extracts queries **only** from
  `office365(.|_)search` (`queries[].query`) and `search_enterprise_*`
  (`arguments.query`) and prints 0 if none are found. On treat the model
  calls **`search_office365`** — the agentic router — whose argument is
  `{"task": "..."}` (a natural-language task, not a `queries[]` array), so
  Foundry extracts nothing → 0, while CoMet saw a tool call → 100.
- *Symptom:* treat-only (or arm-asymmetric) 🔼 on a "did the model reason /
  call a tool" criterion, where the treatment arm has adopted a newer
  orchestration tool name (`search_office365`, `api_tool_search_tools`, …)
  that the Sydney `script`'s tool-name allow-list doesn't recognize.
- *Empirical confirmation:*
  [`_diag_r1_wrong_reasoning.py`](../code/_diag_r1_wrong_reasoning.py)
  replays both policies on the snap-11 packed session: **66 treat rows**
  disagree (`CoMet=100, Foundry=0`), tool names 65×`search_office365` +
  10×`api_tool_search_tools`, reproducing +33.50 exactly; control 98.98 vs
  98.98 (Δ≈0). After the fix CoMet = Foundry on both arms (98.98 / 65.99).
- *Fix (CoMet, since Foundry = semantic truth):* score 100 only when a
  recognized search query is present — replicate Foundry's `extract_queries`
  exactly, including its quirk that `search_enterprise_*` and each
  `queries[]` element count even with an empty `query` string (so presence
  of a recognized search **call**, not non-emptiness of the text, is the
  bar). Applied to `_wrong_reasoning` in `metric_logic.py`; 4 regression
  tests added (router-task→0, non-search→0, empty-queries→0, concrete→100);
  full suite 593 ✅.
- *Reusable check:* when triaging a treat-only 🔼 on a tool-presence
  criterion, dump the disagreeing rows' tool **names** (not just counts) —
  a newer router tool name absent from the Sydney `script`'s allow-list is
  this bug. Distinct from §4.14 (that's first-call-only vs iterate-all on
  the *same* tool; this is an *unrecognized tool name*).

### 4.16 Missing `is_combined_tool` gate on a domain-presence check (agentic router)

A CoMet criterion calls `_domain_in_output(domain)` **unconditionally**,
but the corresponding Sydney `script` only reaches its `domain_in_output`
helper **inside an `is_combined_tool` branch**; outside that branch it falls
back to a narrow legacy-tool substring test. Because CoMet's
`_domain_in_output` returns `True` for the agentic router tool
`search_office365` regardless of context, it over-counts whenever the
treatment model emits **only** `search_office365` (no combined
`office365_search`/`web.search`/…). Same router-tool class as §4.15, but the
defect is a **missing gate** rather than a missing allow-list entry.

- *Canonical case (R2, `meeting_intent_parameter / has_meeting_tool`):*
  Foundry computes `is_combined_tool = any(m in output for m in
  {office365.search, office365_search, web.search, office365.open,
  office365.find})`. If **not** combined → `100 iff "search_enterprise_meetings"
  in output`. Only if combined → `100 iff domain_in_output('meetings')` (which
  treats `search_office365` as a meeting tool). CoMet's `_has_meeting_tool`
  skipped the gate and called `_domain_in_output("meetings", …)` directly, so
  a bare `search_office365` router call scored 100.
- *Empirical confirmation:*
  [`_diag_r2_has_meeting_tool.py`](../code/_diag_r2_has_meeting_tool.py)
  replays both policies on the snap-11 packed session: **223 treat rows**
  disagree (`CoMet=100, Foundry=0`), all `search_office365`-only (no combined
  tool), reproducing +17.63; control +0.87 (11 rows). After the fix CoMet =
  Foundry on both arms (control 95.89, treatment 78.97).
- *Fix (CoMet, since Foundry = semantic truth):* gate the domain check behind
  the existing `_is_combined_tool` helper, mirroring Foundry exactly —
  `if not _is_combined_tool(text): return 100 if "search_enterprise_meetings"
  in text else 0; return 100 if _domain_in_output("meetings", text) else 0`.
  Applied to `_has_meeting_tool` in `metric_logic.py`; 3 regression tests
  added (router-only→0, router+combined→100, combined non-meeting→0); full
  suite 596 ✅.
- *Reusable check:* when a CoMet metric reuses `_domain_in_output` (or any
  helper that treats `search_office365` as positive), confirm the Sydney
  `script` invokes its equivalent **unconditionally** — many gate it behind
  `is_combined_tool`. Sibling meeting/email/file metrics in `metric_logic.py`
  already gate via `_is_combined_tool(...)`; an ungated call site is the tell.
- *People-search variant (stricter than gating):* `people_search_1st_turn`
  needed more than the `is_combined_tool` gate — even **inside** the
  combined branch, `_domain_in_output("people")` returned `True` on its
  `if name == "search_office365": return True` shortcut, counting a bare
  router call with no people-domain query. Foundry's combined loop skips
  everything that isn't `office365.search`/`office365_search`
  (`if ti['tool'] not in (...): continue`) and counts people only from
  actual `queries[].domain`. Fix: a dedicated
  `_combined_tool_domain_present(domain, text)` helper that inspects only
  `office365.search`/`_search` `queries[].domain` and ignores the router
  and legacy tool *names*; point the combined branch at it instead of
  `_domain_in_output`. Use this helper (not `_domain_in_output`) for any
  criterion that must count a *real* combined-tool domain query.

### 4.17 Auxiliary tool calls leaking into the combined-tool domain set

A CoMet helper that builds the **set of domains** issued via the combined
search tool includes auxiliary (non-`office365.search`) tool calls in that
set, but the Sydney `script`'s combined scoring loop explicitly **skips** any
tool that isn't `office365.search`/`office365_search`
(`if ti['tool'] not in ('office365.search','office365_search'): continue`).
So only combined-search query `domain`s count toward Foundry's decision;
router/aggregator calls (`search_office365`, `api_tool_search_tools`,
`api_tool_skills_list_resources`, `generate_response`, …) are invisible to it.

- *Canonical cases (N1 `keywordless_early_binding`, R6 `keyword_early_fanout`,
  both `meeting_prep_recap`):* CoMet's `_combined_tool_normalized_domains` had
  an `else` branch adding the (mapped or raw) auxiliary tool name to the set.
  - **N1** scores `100 iff domains == {"meetings"}`. A correctly-bound
    `office365.search{meetings}`-only row that *also* fired an auxiliary tool
    got `{"meetings", <aux>} != {"meetings"}` → CoMet 0 vs Foundry 100
    (**CoMet lower** — the −4.21/−6.86 gap).
  - **R6** scores `100 iff meetings ∈ domains and ∃ other domain`. The same
    leaked auxiliary tool *satisfied* the "second domain" requirement, so a
    meetings-only row scored 100 vs Foundry 0 (**CoMet higher** — the +3.85
    treat gap). One bug, opposite signs on the two sibling criteria.
- *Empirical confirmation:*
  [`_diag_n1_keywordless.py`](../code/_diag_n1_keywordless.py) replays both
  policies on the snap-11 packed session and cross-checks the Foundry replica
  against Foundry's **stored `scriptOutput`** (0 mismatches / 452 rows / arm).
  N1: 19 ctrl + 31 treat disagree rows, all `CoMet=0/Foundry=100`, every one an
  `office365_search{meetings}` call plus an auxiliary tool, reproducing
  −4.20/−6.86 exactly.
- *Fix (CoMet, since Foundry = semantic truth):* drop the `else` branch so
  `_combined_tool_normalized_domains` collects **only** `office365.search`/
  `office365_search` query domains, mirroring the script's skip. Verified with
  the real fixed functions over the packed data: both criteria → Δ=+0.00 on
  both arms (N1 62.17/48.45, R6 55.77/26.92). 3 regression tests added
  (meetings+aux→100 for N1; meetings+aux→0 and meetings+emails+aux→100 for R6);
  full suite 599 ✅.
- *Reusable check:* when a metric reduces combined-tool output to a **domain
  set**, confirm the Sydney `script`'s combined loop counts only
  `office365.search`/`office365_search` entries — its `parse_*_combined`
  generator may *yield* auxiliary tools that the scoring loop then `continue`s
  past. A helper that maps those auxiliary names into the set is the bug, and
  it can flip sign between a "sole domain" criterion (N1) and a "≥2 domains"
  criterion (R6).
- *Legacy/non-combined branch can lag the combined branch.* The same
  aux-tolerance fix must be applied to **both** branches of a script.
  `WebOnly` had an aux-tolerant **combined** branch (filtering to
  `COMBINED_TOOL_MARKERS`) but its **legacy** `else` branch still used
  `all(tool == "search_web")`, so a harmless auxiliary tool (`open`,
  `python`, `api_tool_search_tools`) alongside `search_web` broke `all(...)`
  → Foundry 0 while CoMet (which ignores aux: `has_web and not has_work`)
  scored 100. Fix the legacy branch to mirror the combined one:
  `has_web = any(t == "search_web") ; has_work = any(t.startswith("search_enterprise")) ; print(100 if has_web and not has_work else 0)`.
  When triaging an aux-tool gap, check **which** branch the row hit — a
  row with no combined markers falls into the legacy branch, which is the
  one most likely to still be over-strict.

### 4.18 Per-call `print` (last-wins) + first-call `raise` vs aggregate-all-calls (Foundry scripting accident)

A Sydney `script` that loops over `office365_search` calls can diverge from a
CoMet metric that flattens **all** calls if the script makes its decision
**per call** instead of **once over the union**. Two coupled bugs:

- **`print` inside the per-call loop.** Foundry takes the **last** printed
  line as the score, so a multi-call row is scored by its *last*
  `office365_search` call only — earlier calls are silently overwritten.
- **`raise` inside the per-call loop** (e.g.
  `raise ValueError("no meeetings function found in input")` when a single
  call has no meetings-domain queries). The raise **terminates** the script:
  the row is dropped only if the **first** call lacks meetings queries; if an
  earlier call already printed, that stale print becomes the score.

- *Canonical case (R7 `meeting_keywords_past`, both
  `miss_"past"_test(strict)` and `(loose)`):* CoMet's `_miss_past_test_*`
  collect every meetings-domain query across **all** `office365_search`
  calls then apply `all(...)` / `any(...)` once, skipping the row only if
  there are no meetings queries anywhere. Foundry's script printed per call
  (last wins) and raised on the first meetings-less call. On the 30 ctrl /
  36 treat rows with ≥2 search calls the two policies diverge — symmetric,
  opposite signs (loose +2.48 ctrl, strict −2.57 ctrl).
- *Empirical confirmation:*
  [`_diag_r7_past_loose.py`](../code/_diag_r7_past_loose.py) reproduces the
  Foundry semantics (last-print-wins, raise-terminates) against Foundry's
  stored `scriptOutput` (0 mismatches / arm).
- *Fix (Foundry, exceptionally — this is a scripting accident, not semantic
  truth):* restructure both scripts to accumulate
  `all_meetings_domain_queries` across **all** calls, then make a single
  decision (`print(0)`/`print(100)` once; skip only if the union is empty),
  mirroring CoMet **and** the already-correct sibling
  `meeting_keywords_in_the_next_week` scripts. Verified by executing the
  edited script text over the packed data
  ([`_diag_r7_verify_foundry.py`](../code/_diag_r7_verify_foundry.py)):
  both criteria → Δ=+0.00 both arms (strict 74.75/59.00, loose 79.80/73.00),
  0 row mismatches, denoms aligned (99/99, 100/100). No CoMet change.
- *Reusable check:* when a metric flattens all `office365_search` calls but
  the Sydney `script` `print`s or `raise`s **inside** the call loop, the
  script scores by the last call and drops on the first empty call. Compare
  against the sibling `meeting_keywords_in_the_next_week` scripts, which
  accumulate once and decide once — that is the correct pattern. This is the
  rare case the fix lands on the **Foundry** side.

### 4.20 Failed-inference rows: both sides must drop the *identical* population

`prompt_tokens == 0` rows (the pre-eval emitted a well-formed but empty
payload `{"tool_calls": [], "Usage": {"prompt_tokens": 0, …}}` — inference
never ran) must be dropped by **both** pipelines, on **keep-row recall**
criteria especially. The subtle trap is that "both sides drop failed rows"
is **not sufficient** — they must drop the **same rows**, or the
denominators still diverge and small-n recall criteria flip to ⚠️/❌ on a
**byte-identical numerator** (pass-count = `round(pct·denom/100)` equal on
both sides → pure §4.2 denominator artifact, not a scoring bug).

- *Direction 1 — Foundry under-drops (CoMet higher).* Foundry's keep-row
  recall script `print(0)`s a failed row (counts it as a miss) while CoMet
  drops it at the data layer. Fix: extend the Foundry per-criterion guard to
  `raise SystemError` when `prompt_tokens == 0 and not tool_calls` (the
  naïve `if not """{{text}}""".strip()` guard does **not** fire — `{{text}}`
  is the non-blank empty payload). The `FOUNDRY-CoMet-ALIGN-O-K` skip block
  is the reference; apply it to **every** keep-row recall criterion,
  including LLM-judge ones (e.g. `meetings_rsvp`) that also score failed rows
  as 0.
- *Direction 2 — Foundry over-drops (CoMet higher again, opposite denom
  sign) — ROOT-CAUSED + FIXED.* After adding the Foundry skip, Foundry
  dropped a **superset** of CoMet's drops on `prompt_triggering_meetings`
  `meetings_recall`: CoMet kept 1625, Foundry kept only 1579 — same
  byte-identical numerator (1459), smaller Foundry denominator → CoMet
  lower. Ground-truth decomposition of the 46-row gap (cross-checked
  per-row against CoMet's results TSV,
  [`_issueBrev_groundtruth.py`](../code/_issueBrev_groundtruth.py)):
  - **45 of 46 = Foundry over-drop of *responding-only legit recall
    misses*.** These rows have a `fluxv3:responding` DeepLeo metric — the
    model **ran and answered without invoking any meetings tool** (a real
    recall miss). CoMet correctly keeps them scoring 0; Foundry wrongly
    discarded them.
  - **1 of 46 = CoMet under-drop** of a genuine failed-inference row (no
    metric at all) — negligible, a CoMet harness edge.

  **Root cause (Foundry side).** `extract_tool_calls_from_deep_leo` read
  token usage **only** from the first `fluxv3:invokingfunction` metric. A
  responding-only turn emits a single `fluxv3:responding` metric and **no**
  `invokingfunction` metric, so `usage` stayed `{prompt_tokens: 0}` even
  though the turn ran a full inference — the smoking-gun payload carried
  `{"promptTokenCount": 16807, "completionTokenCount": 85,
  "toolInvocations": []}`. The session skip `prompt_tokens == 0 and not
  tool_calls` then mistook the legit no-tool answer for a dead row and
  dropped it, **inflating Foundry recall** (here 92.40% vs the true
  89.84%) across the whole keep-row recall cluster (shared extractor).

  **Fix (implemented).** In `extract_tool_calls_from_deep_leo`, when no
  `invokingfunction` metric has been seen, capture token usage from the
  `responding` metric as a fallback (an invoking metric, if one appears,
  still takes precedence). `prompt_tokens` is then a faithful
  "did inference run?" signal: a legit no-tool answer reports
  `prompt_tokens > 0` (preserved as a recall miss), while a row where
  inference never ran reports `prompt_tokens == 0` (still dropped).
  Result: Foundry keep 1579 → **1624** (Δ+45), gap → 1, recall 92.40% →
  **89.84%** ≈ CoMet 89.78%; no regression (no previously-kept row changed,
  no dead row started being kept). Regression tests:
  `TestRespondingOnlyUsage` in `local/tests/test_preeval_extraction.py`.
  **Confirmed in snap 3** (§5.4): the full deterministic-recall cluster is
  now Δ≈0 — `meetings_recall` −0.06, `record_memory_recall` +0.00 (was the
  lone ❌), `files_recall`/`WorkOnly`/`chat_recall`/`emails_recall`/
  `email_mailbox_recall`/`trigger_rate` all +0.00.

  **Triage trap.** Do **not** decide direction by reading `prompt_tokens`
  on the gap rows — under the *un*-fixed extractor a legit responding-only
  miss *also* reports `prompt_tokens == 0`, so that test would wrongly tell
  you to widen CoMet's drop and replicate the Foundry bug. The reliable
  discriminator is the **metric shape**: a `fluxv3:responding` DeepLeo
  metric present (model ran → keep, score 0) vs **no** DeepLeo metric at
  all (inference never ran → drop).
- *Reusable check / triage:* run
  [`_audit_550341_numerators.py`](../code/_audit_550341_numerators.py) first
  on any snapshot with many recall ⚠️/🔼 — equal pass-counts ⇒ this pattern
  (denominator alignment, no criterion-logic change); unequal ⇒ a real
  scoring divergence. Small denominators (`record_memory_recall` n=42,
  `WorkOnly` n=38) amplify a few extra rows into ❌; the same effect is
  invisible on large-denominator recall criteria.

### 4.21 LLM-judge reimplementation: identical full input, then irreducible model variance

When CoMet reimplements an LLM-judge criterion, the only way to track
Foundry is to feed the judge the **identical full input** Foundry feeds and
gate on the **identical row population** — then accept that the residual
delta is irreducible judge-model variance, not a bug to chase.

- *Feed the full blob, don't pre-extract.* Foundry's judge prompt is
  typically `… {{text}}` with `{{text}}` = the **full tool-calls JSON blob**;
  the judge locates the relevant query itself. A CoMet reimplementation that
  pre-extracts a single field (e.g. the *first* meetings query) and sends
  only that diverges whenever extraction misses (combined-tool /
  `search_office365` router shapes) or there are multiple queries. Fix: feed
  the same full blob (as `query_correctness` / `time_range` already do) and
  gate on tool-call **presence**, not on extraction success. (`meetings_rsvp`
  `_build_rsvp_messages` + `preprocess` were fixed this way.)
- *Identical prompt + identical input ⇒ the only remaining variable is the
  judge model.* `query_correctness` is the natural control: CoMet's
  `prompts/query_correctness.md` is byte-for-byte the Foundry system prompt
  and feeds the same input, yet still differs on n=21 — the two judge
  deployments grade the 0/25/50/75/100 buckets differently. This is
  irreducible LLM subjectivity, amplified on small n; not fixable without
  pinning the identical judge deployment, and **not** a logic bug.
- *Byte-matching the prompt **text** is necessary but **not** sufficient — the
  message **role and shape** must match too.* Foundry sessions deliver the
  judge prompt in different shapes: `system`+`user` (e.g.
  `attendance_in_meetings`, `query_correctness`), a lone `system`
  (`time_qualifier_check`), a lone `user` (`tool_tense_aligned(time_hints)`),
  or a single `assistant` continuation (`language_match`, `time_range_check`,
  the OOF criteria). CoMet's `_build_assessment_messages` defaults to
  `system` + a `{{text}}` `user` echo — which faithfully reproduces only the
  `system`+`user` sessions. For `language_match` that default both (a) changed
  the role (`assistant`→`system`) and (b) **duplicated the tool-call blob**
  (once inline where the md ends `… {{text}}`, once in the user echo), shifting
  the judge to **CoMet +13.70/+13.52** (the largest |Δ| in snap 2, a ~4× jump
  from the ≈+3.5 band on 517819). Fix: deliver such criteria as a **single
  message with the Foundry role** and no echo (see
  `_CRITERION_SINGLE_MESSAGE_ROLE`). `language_match` is the only assessment
  criterion that is both `assistant`-role **and** embeds its input inline, so
  it was the lone large divergence; `time_qualifier_check`/`chi_lb` also embed
  `{{text}}` inline but are `system`-role, so the default `system` rendering
  already matched (they stayed NUM-EQ). **Snap-3 update (§5.4): the single-

##### Open item — `language_match` — ROOT-CAUSED + CLOSED: judge-model mismatch (GPT-5 vs GPT-4.1)

The one residual **numerator** divergence in the current snapshot, and it is
**not irreducible same-model judge noise** — it is a **judge-model
configuration mismatch**:

| | Foundry session | CoMet `metric_spec.yaml` |
|---|---|---|
| judge model | **`dev-gpt-5-chat-jj`** (GPT-5) | **`dev-gpt-41-shortco-2025-04-14`** (GPT-4.1) |
| temperature | 0 | 0 (matches) |
| max_tokens | 1024 | **300** |

The two pipelines feed the judge the same prompt text and the same tool-call
blob (the `_CRITERION_SINGLE_MESSAGE_ROLE` fix made the role/turn-count match),
but they call **different model families**. Verified by reading the Foundry
session `prompt.model` for every LLM criterion
([`_lang_judge_models.py`](../../../../../../Foundry/local/code/_lang_judge_models.py)):
**19 of 20** Foundry LLM criteria judge with `dev-gpt-5-chat-jj` (the lone
exception, `attendance_in_meetings`, uses `dev-gpt-4o-gg`); CoMet judges **all**
of them with GPT-4.1. So the mismatch is uniform — what makes `language_match`
uniquely the worst is the **score shape + task**, not a per-criterion bug:

- **Binary 0/100 score.** Every row the two models disagree on swings the full
  100 points, so a systematic capability gap shows up at full amplitude.
  Graded criteria (`query_correctness` 0/25/50/75/100, etc.) absorb the same
  model disagreement into small per-row deltas that partially cancel and stay
  in band despite the *identical* GPT-5↔GPT-4.1 mismatch.
- **Subtle, capability-sensitive task.** The judge must decide whether the
  tool **query** preserves the *German* keywords of a German utterance.
  GPT-4.1 is **systematically more lenient** (passes 91.6%/92.6%) than GPT-5
  (passes 82.6%/74.4%) at detecting cross-language keyword drift — a
  **directional** bias (~11 rows flip 0→100), not random sampling noise, which
  is exactly why it exceeds the ~3–9 pp same-model band. The other large-ish
  GPT-5 ⚠️ (`time_range_check` −6/−5) is the same story.

The **3-/5-row CoMet denom drop** is a secondary effect of `max_tokens=300`
(vs Foundry 1024): if GPT-4.1's reasoning runs past 300 tokens before it emits
`lang_score:`, the parse fails → `_SKIPPED` → the row is dropped from CoMet's
denominator. Raising `max_tokens` should recover those rows.

**GPT-4.1 is CoMet's platform-standard judge — this is by design, not a
per-metric oversight.** Surveyed every `metric_spec.yaml` / `metric_config.yaml`
in the CoMet repo (~125 specs): **~105 use `dev-gpt-41-shortco-2025-04-14`**
(GPT-4.1 short-context, the default), ~10 use the GPT-4.1 long-context variant,
4 use GPT-4o, and the GPT-5/5.1/5.2 deployments appear in **only 4** metrics
total. **Exactly one** CoMet metric (`planner_quality_2pt`) uses Foundry's
`dev-gpt-5-chat-jj`. So the GPT-5↔GPT-4.1 gap is a deliberate
platform-standardization choice on CoMet's side (cost / latency / availability),
not a bug in `bizchat_reasoning_checklist`.

**Recommendation — classify as a documented, expected judge-deployment mismatch
(no code change).** This is the §4.21 "identical input ⇒ residual is the judge
model" case, made fully visible by the binary 0/100 score. Do **not** chase it
as a logic bug, and do **not** override the metric to GPT-5 lightly: that would
make `bizchat_reasoning_checklist` an outlier against ~105 other CoMet metrics
and break the platform's GPT-4.1 standardization. A judge-model override to
`dev-gpt-5-chat-jj` (+ `max_tokens` 1024) is justified **only** if byte-parity
with the Foundry-collected labels is a hard requirement for this metric; since
`llm.model` is **global** to all 16 of its LLM criteria, any such switch must be
re-validated against the currently-in-band criteria in the next snap (it should
*improve* alignment everywhere, since Foundry calibrated them all on GPT-5).
Absent that requirement, the residual is expected and the item is **closed as
judge-deployment variance**.
